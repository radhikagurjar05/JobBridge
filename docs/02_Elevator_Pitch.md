# 02 — Elevator Pitch (Interview-Ready Explanations)

## 30-Second Explanation
"JobCatch is a Flask web app I built where you upload your resume — PDF or Word — and it instantly tells you which of 25 job roles fits you best, gives your resume a score out of 100, and shows you exactly which skills you have and which ones you're missing for that role. It also has a login system and an interview-prep section with practice questions. The matching engine isn't a black-box AI model — it's a transparent keyword-counting algorithm, so I can explain exactly why it made every single prediction."

## 1-Minute Explanation
"JobCatch is a full-stack Flask application for job seekers. You register or log in, then upload your resume as a PDF or DOCX file. The backend uses PyPDF2 or python-docx to pull out the raw text, then runs it through my own analysis engine in `app/ml/predict.py`. That engine does three things: it counts keyword matches against 25 role dictionaries to predict your best-fit role, it checks for resume structure — things like whether you have an email, a phone number, a skills section, an education section — and gives a score out of 100, and it compares your resume's text against the keyword list for your predicted role to show found vs. missing skills. Every upload gets saved to a MySQL database along with the predicted role and score, so the dashboard can show your history and average score over time. There's also a separate interview-prep page where you pick a role and get real Q&A pairs to practice with."

## 2-Minute Explanation
"JobCatch solves a problem a lot of students have: you don't really know if your resume is good, or which role it's actually aimed at, until a recruiter tells you — usually after you've already been rejected. So I built a tool that gives that feedback instantly.

Architecturally it's a classic Flask app using the **application factory pattern** — `create_app()` in `app/__init__.py` builds the Flask app, loads config from environment variables via `python-dotenv`, and registers three blueprints: `auth` for login/register/logout, `main` for the homepage and dashboard, and `resume` for upload, history, and interview prep.

For the database I didn't use an ORM like SQLAlchemy — I used the raw `mysql-connector-python` driver with plain SQL, so every query is visible in `app/models.py`. There are two tables: `users`, which stores name, email, and a hashed password, and `resume_uploads`, which stores every resume a user has uploaded along with its predicted role and score, linked by a foreign key with `ON DELETE CASCADE`.

The 'AI' part is intentionally not a machine learning model. It's a dictionary of 25 job roles, each mapped to about 15 keywords — things like Python, Django, Flask for a 'Python Developer' role. When you upload a resume, I clean the text, lowercase it, and count how many keywords from each role appear. The role with the highest count wins. If nothing matches, it falls back to 'General / Other'. I chose this over a trained model because it's 100% explainable — I can always tell you exactly why a prediction happened, which matters a lot for a resume tool where users want to trust the result.

On top of that, resume scoring checks seven things — email present, phone present, skills section, education section, experience section, length over 250 words, and projects/achievements — each worth different points, totaling 100.

Security-wise, passwords are hashed with Werkzeug's `generate_password_hash` (scrypt-based), never stored in plain text, and authentication state is kept in Flask's signed session cookie. Login is protected with a custom `login_required` decorator.

The frontend is plain HTML/CSS/JavaScript with Jinja2 templates — no React or Vue — with a dark mode toggle stored in `localStorage` and a drag-and-drop upload zone."

## 5-Minute Explanation
"JobCatch is a resume-analysis and career-guidance web application I built with Flask. I'll walk through the problem, the architecture, the core algorithm, the data model, and the security decisions.

**The problem**: job seekers often don't know which role their resume actually targets, whether it's structurally complete, or which specific skills they're missing — and getting that feedback from a person is slow and often costs money. JobCatch automates the first pass of that feedback.

**The architecture** follows the Flask 'application factory' pattern instead of a single global `app = Flask(__name__)`. `create_app()` in `app/__init__.py` creates the app, loads `Config` (which itself pulls `SECRET_KEY` and MySQL credentials from environment variables via `python-dotenv`, so nothing sensitive is hardcoded), registers `app.teardown_appcontext(close_db)` so the database connection always closes at the end of a request, registers three blueprints (`auth_bp`, `main_bp`, `resume_bp`), and finally calls `init_db(app)`, which connects to MySQL and runs `CREATE TABLE IF NOT EXISTS` for `users` and `resume_uploads` — so the schema self-heals on first run without needing a separate migration step.

**The request flow for the core feature (resume upload)** starts at `GET /upload`, which just shows the drag-and-drop form. On `POST /upload`, the route in `app/resume/routes.py` validates that a file was attached and that its extension is `.pdf` or `.docx` (checked against `Config.ALLOWED_EXTENSIONS`), then calls `extract_text()`, which uses `PyPDF2.PdfReader` for PDFs (looping over every page and concatenating `extract_text()`) or `python_docx.Document` for Word files (joining every paragraph's text). If extraction returns nothing — which happens with scanned/image-only PDFs — the user gets a friendly flash message instead of a crash. The extracted text then goes into `analyze_resume()` in `app/ml/predict.py`, which is really three small functions composed together: `predict_role()` counts keyword hits per role from the `ROLE_KEYWORDS` dictionary in `app/ml/data.py` and returns whichever role has the most hits (or 'General / Other' if none match at all); `compute_score()` runs seven independent regex/substring checks — email regex, phone regex, presence of the word 'skill', education-related words, experience-related words, a 250-word minimum, and achievement-related words — each worth 10-20 points, summing to a maximum of 100; and `extract_skills()` re-uses the predicted role's keyword list to split it into 'found in resume' vs 'missing' for the skill-gap section. The final combined result dictionary is both rendered back to the user immediately and persisted via `save_upload()` into the `resume_uploads` table together with the logged-in user's ID.

**Data model**: two tables only. `users(id, name, email UNIQUE, password_hash, created_at)` and `resume_uploads(id, user_id FK→users.id ON DELETE CASCADE, filename, upload_time, predicted_role, resume_score)`. No ORM — I use `mysql-connector-python` directly with parameterized queries (`%s` placeholders), which is also how I avoid SQL injection. Dashboard stats (`get_upload_stats`) and history (`get_user_uploads`) are just aggregate/`SELECT ... ORDER BY` queries scoped to `user_id`.

**Security decisions**: passwords are hashed with Werkzeug's `generate_password_hash`/`check_password_hash` (scrypt), never compared or stored in plain text. Login state lives in Flask's signed session cookie (`session['user_id']`), and a `login_required` decorator in `app/main/routes.py` guards `/dashboard`, `/upload`, and `/history`. File uploads never touch disk — the file is read into memory (`io.BytesIO`) and only the extracted text and the `secure_filename()`-sanitized name are kept, which removes a whole class of path-traversal and unrestricted-file-write risks. I'm upfront in my own documentation that this project does **not** implement CSRF tokens, rate limiting, email verification, or the Google OAuth flow that's referenced in comments and `.env.example` — those are known gaps, not secrets, and I'd talk through how I'd add them (Flask-WTF for CSRF, Flask-Limiter for rate limiting) if asked.

**Frontend**: server-rendered Jinja2 templates extending one `base.html`, vanilla CSS with light/dark theme CSS variables toggled via a `data-theme` attribute and persisted in `localStorage`, and a small amount of vanilla JS for drag-and-drop upload UX and for fetching interview questions from a JSON endpoint (`/api/questions?role=...`) without a page reload.

If I were scaling this or hardening it for production, the first things I'd add are: CSRF protection, connection pooling instead of one connection per request, pagination on the history table, and turning the keyword engine into a pluggable interface so a real ML model could be swapped in later without changing the routes."
